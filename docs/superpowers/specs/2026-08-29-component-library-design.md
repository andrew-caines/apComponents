# apComponents — System Design

**Date:** 2026-08-29
**Status:** Design approved, not yet implemented
**Decisions:** [`docs/adr/`](../../adr/README.md) — ADR-0001 through ADR-0017

This document describes the system. The *why* behind each decision lives in the ADRs; this is the shape of the thing and the order it gets built in.

---

## 1. What this is

A React + TypeScript component library for Atlas HXM products, consumed as a vendored git submodule. It ships:

- A **theme generator** — one brand colour in, a complete accessible token set out
- A **component set** built on Base UI primitives, styled from those tokens
- A **motion system** with named semantic motions and enforced reduced-motion
- **Formatters, hooks, notifications and icons** shared across every product

Everything renders correctly in single-page apps and in React Router 8 server-rendered apps.

## 2. Architecture

```
┌───────────────────────────────────────────────────────┐
│  @ap/tokens        no React, no DOM, no bundler       │
│  brand colour → OKLCH engine → token tree → CSS text  │
└──────────────────────┬────────────────────────────────┘
                       │
        ┌──────────────┴──────────────┐
        │                             │
┌───────▼─────────┐          ┌────────▼──────────────────┐
│  @ap/motion     │          │  theme.css (build output) │
│  dual-emit:     │          │  Tier 1 / 2 / 3 vars      │
│  CSS + JS       │          │  light · dark · P3        │
└───────┬─────────┘          └────────┬──────────────────┘
        │                             │
┌───────▼─────────────────────────────▼─────────────────┐
│  @ap/react                                            │
│  ┌─────────────────────────────────────────────────┐  │
│  │ Base UI primitives  (behaviour + ARIA)          │  │
│  ├─────────────────────────────────────────────────┤  │
│  │ vanilla-extract .css.ts → static classes        │  │
│  │ reading var(--ap-*)                             │  │
│  ├─────────────────────────────────────────────────┤  │
│  │ compound components · hooks · format · icons    │  │
│  │ ThemeProvider · LocaleProvider · Notifications  │  │
│  └─────────────────────────────────────────────────┘  │
└───────┬───────────────────────────────────────────────┘
        │  file: protocol from vendor/apComponents
┌───────▼───────────────────────────────────────────────┐
│  Product app   —   vite.config: apComponents()        │
│  SPA  or  React Router 8 framework mode               │
└───────────────────────────────────────────────────────┘
```

**The load-bearing idea:** the boundary between theme and component is *CSS custom properties*, not JavaScript. That single choice is what makes SSR trivial, theming runtime-switchable, dark mode free, and the whole thing zero-runtime.

## 4. Component anatomy

Every component directory looks the same:

```
components/Button/
├── Button.tsx          'use client'; Base UI + recipe classes
├── Button.css.ts       vanilla-extract recipe, reads var(--ap-button-*)
├── Button.tokens.ts    Tier 3 token declarations
├── Button.stories.tsx  gallery, controls, axe, play() interactions
├── Button.test.tsx     unit
└── index.ts
```

Uniformity is the point: a contributor who has read one component has read all of them, and the review checklist is the same every time.

## 5. Build order

Six phases. Each ends with a verification gate passing, so nothing is built on an unproven foundation.

### Phase 1 — Token engine (`@ap/tokens`)
The colour engine, ramp generation, gamut mapping, APCA and WCAG implementations, non-colour scales, CSS emitter. Also the typography tokens and font-metric table ([ADR-0015](../../adr/0015-typography.md)), the z-index scale ([ADR-0016](../../adr/0016-cascade-layering-focus.md)) and breakpoint constants ([ADR-0017](../../adr/0017-responsive-adaptive.md)). No React, no components.

**Done when:** gates 1–3 pass and `reports/contrast.md` shows every default-theme pairing passing AA in both modes.

*This phase is deliberately first and deliberately isolated. If the colour engine is wrong, everything built on it is wrong, and it is far cheaper to discover that against a data snapshot than against fifteen components.*

### Phase 2 — Build plumbing
vanilla-extract wiring, `@ap/vite` preset, `theme.css` emission, the two fixture apps, CI skeleton.

**Done when:** gate 8 passes with a single trivial component. The submodule consumption path is proven before anything depends on it.

### Phase 3 — Motion system (`@ap/motion`)
Primitives, named semantic motions, dual-emit, reduced-motion token overrides.

**Done when:** a test asserts the CSS and JS emissions are equivalent, and that every motion token has a `prefers-reduced-motion` definition.

### Phase 4 — Vertical slice
`ThemeProvider`, `LocaleProvider`, `ApProvider`, the icon set, and **three** components chosen to exercise everything: **Button** (recipe variants, `render` passthrough), **Field + Input** (compound context, ARIA wiring, uncontrolled semantics), **Dialog** (portal, focus trap, enter/exit motion, SSR portal behaviour).

**Done when:** gates 4–7 pass. This is the checkpoint where the architecture is either right or gets corrected — cheaply, across three components rather than fifteen.

### Phase 5 — Remaining v1 components
Textarea, Select, Checkbox, Radio, Switch, Toast, Tooltip, Popover, Tabs, Accordion, Spinner. Plus `NotificationProvider`, the hooks and the formatters.

**Done when:** all ten gates pass over the full set.

### Phase 6 — Documentation
Storybook build and Pages deployment, MDX guides (theming, SSR rules, colour theory, migration), the interactive theme-generator page.

**Done when:** Storybook is live on GitHub Pages and CI deploys it on merge to `main`.

## 6. Verification

Full detail in [ADR-0014](../../adr/0014-verification-gates.md). The summary:

| Phase | Gates that must pass |
|---|---|
| 1 | tokens, contrast, gamut |
| 2 | consumer integration |
| 3 | motion dual-emit equivalence |
| 4 | unit, a11y, SSR smoke, SPA smoke |
| 5 | all ten |

**Proof artifact:** a green CI run on `main` with gates 1–8 passing, the deployed Storybook, and `reports/contrast.md` from that run.

## 7. What is deliberately not in v1

| Deferred | Why |
|---|---|
| React Server Components | No consumer needs it; [ADR-0003](../../adr/0003-zero-runtime-styling.md) already satisfies its hardest constraint, so revisiting is scoped |
| Density mode (compact/comfortable) | Space ramp is ratio-derived, so a global density axis is a later scale change ([ADR-0017](../../adr/0017-responsive-adaptive.md)) |
| Grid/layout components | v1 exports breakpoint constants and hooks only; apps own page layout |
| Table, Pagination, Card, Badge, Avatar, EmptyState | v2. Table is its own sub-project (sorting, virtualisation, sticky columns) |
| High-contrast colour mode | Scale design accommodates it as a third set of lightness targets |
| Docusaurus prose site | Storybook MDX suffices until it does not |
| A theme-generation CLI | Thin wrapper over `generateTheme`; add when a product asks |
| Publishing to a registry | `file:` → version range is a packaging change, not a rewrite |
| RTL / i18n layout | Base UI supports it; we should design tokens with logical properties from the start so this stays cheap |

## 8. Risks

| Risk | Mitigation |
|---|---|
| The `file:` symlink + Vite SSR externalisation seam breaks | Gate 8 exists specifically to watch it, and runs on every PR |
| Base UI has an accessibility or behaviour bug | Gate 5 catches regressions even when they originate upstream; Radix is the documented fallback ([ADR-0004](../../adr/0004-base-ui-primitives.md)) |
| Colour engine produces coherent-but-ugly themes | Phase 1's interactive Storybook page exists to eyeball output early; APCA generation targets perception, not just arithmetic |
| Token contract churns and breaks consumers | Tier 2 is the published contract and is versioned; Tier 1 is explicitly internal |
| Storybook upgrade burden | Confined to the private `docs` workspace, never in a published package |

## 9. Open questions

None blocking Phase 1. Two worth settling before Phase 4:

1. **Default brand seed.** The direction is set — calm, data-dense, cool-tinted neutrals, blue-family primary — but the actual seed hex is undecided. Cheapest resolution: generate three candidates in Phase 1 and pick by looking at them.
2. **Logical properties for RTL.** Authoring with `inline-start`/`block-end` from day one costs nothing now and makes RTL cheap later. Recommend adopting it as a Phase 2 convention unless there is a reason not to.
